## Phase 3 — Poison detection module — DONE

Four detection signals, fused into a single per-chunk `poison_score`, plus a standalone LLM-as-judge baseline for comparison:

- `src/detection/config.py`: new centralized `DetectionConfig` frozen dataclass (first shared config module in the repo, vs. the existing per-module `os.getenv` pattern) — every threshold/weight/model-name used across the detection module lives here, `os.getenv`-backed via `field(default_factory=...)` so each instantiation re-reads the environment (a plain `os.getenv(...)` default expression would only evaluate once at class-definition time — hit this as a real test failure, fixed). Every detection function takes an optional `config: DetectionConfig` param instead of reaching for a global, so Phase 9's cost-accuracy sweep can construct alternate config instances directly. `OPENAI_API_KEY` deliberately never lives on this dataclass (it gets serialized into eval-result JSON).
- `src/detection/perplexity.py`: `PerplexityScorer` wraps a small HF causal LM, default `distilgpt2` (not `gpt2` — empirically the stronger/faster choice on this CPU-only box). `normalize_perplexity()` uses fixed config-driven anchors, not batch min-max, so scores stay comparable across batches of different size/composition.
- `src/detection/cluster_anomaly.py`: combines a faiss k-NN density signal with a `DBSCAN` small-cluster-membership signal. Standard `LocalOutlierFactor`/`IsolationForest` were benchmarked and explicitly rejected — both scored *below* the 21% base rate on this manifest, because they hunt for sparse-region outliers while this data's actual poison pattern is dense micro-clusters (near-duplicate PoisonedRAG variants targeting the same question) inside a diffuse background.
- `src/detection/classifier.py`: lightweight `StandardScaler` + `LogisticRegression(class_weight="balanced")` on chunk embeddings stacked with normalized perplexity/cluster scores — not a fine-tuned HF transformer (only 280 labeled examples, 60 positive, CPU-only box). Evaluated via stratified 5-fold CV with `cross_val_predict` rather than a single 80/20 split (60 positives make a single split's held-out metric too high-variance); a separate model fit on the full manifest is what gets persisted to `models/poison_classifier.joblib` for production scoring, but its in-sample predictions are never reported as a metric.
- `src/detection/pipeline.py`: `DetectionPipeline` class fuses the three signals via `fuse_scores()`, a pure function that renormalizes weights when the classifier is unavailable (it's genuinely optional). The LLM-judge is deliberately *not* a fusion input — it's a standalone comparison baseline per the exit-criteria wording.
- `src/detection/llm_judge.py`: OpenAI-based judge (per `PLAN.md`'s literal Phase 3 wording — this is *not* a deviation from `PLAN.md` itself, only from the superseded `plan_2.md` and `pyproject.toml`'s prior Anthropic-only stance; new `openai` dependency added). Structured JSON output (`poison_likelihood` float, not an ambiguous separate confidence+bool pair), `ThreadPoolExecutor`-parallelized, with an on-disk cache (`eval/benchmarks/.judge_cache.json`, gitignored) to avoid re-spending API budget across repeated dev runs.
- `eval/run_eval.py`: `--stage detection` CLI. Computes embeddings/perplexity/cluster-anomaly once and reuses them across the classifier and fusion steps. Critically, the "fused pipeline" report row uses the classifier's **CV out-of-fold** scores, not `DetectionPipeline`'s live full-fit-model prediction — using the latter would leak the classifier's own training data into the fused score's reported metric.
- **Real bug caught during verification**: training via `python -m src.detection.classifier train` pickled `ClassifierArtifact` with its module recorded as `__main__` (since that file was the entry point), which then failed to unpickle from a different entry point (`eval/run_eval.py`) with `AttributeError: module '__main__' has no attribute 'ClassifierArtifact'`. Fixed by persisting a plain dict of the artifact's fields instead of the dataclass instance.
- Tests: `tests/detection/{test_config,test_perplexity,test_cluster_anomaly,test_classifier,test_pipeline,test_llm_judge}.py`, 21 tests (19 run locally + deterministically; `test_llm_judge.py`'s 2 tests skip via `pytest.skip(...)` in a fixture when `OPENAI_API_KEY` is unset, mirroring the existing Qdrant-unreachable skip pattern).
- New deps installed: `faiss-cpu`, `openai`, `joblib` (scikit-learn was already installed). New files: `.env.example` (didn't exist before despite `.gitignore` already carrying the exception for it).

## Phase 4 — Provenance-gated retrieval policy engine — DONE

Live defense layer sitting between Qdrant similarity search and generation. Full design went through two scoped Plan-agent passes plus independent verification against the actual installed `qdrant-client==1.18.0` API, the real `cluster_anomaly.py`/`pipeline.py` source, and the real `poison_manifest.json` contents before any code was written; final plan approved via Plan Mode as required by `PLAN.md`.

- `src/retrieval/config.py`: new `PolicyConfig` frozen dataclass, mirroring `DetectionConfig`'s exact pattern (`field(default_factory=lambda: _env_*(...))`, never a bare `os.getenv(...)` default). 13 tunable fields: retrieval sizing, a categorical `allow_quarantined_tier` override, four poison-score band thresholds (separate downweight/hard-drop cutoffs for verified vs. unverified tiers — verified strictly more permissive), a downweight-ramp floor, three frequency-anomaly knobs, a cluster-anomaly reference-sample size, and — per "every threshold must be config-driven" taken literally — the two Phase-4 exit-criteria thresholds themselves (`EXIT_CRITERIA_ASR_REDUCTION_PP_MIN`, `EXIT_CRITERIA_PRECISION_LOSS_RELATIVE_PCT_MAX`). Deliberately decoupled from `DetectionConfig.poison_score_threshold` (0.5) — the policy engine reads `ChunkScore.poison_score` directly and never calls `DetectionPipeline.flag()`, since "is this chunk poisoned for eval purposes" and "what should retrieval do about it" are different, tier-conditional questions.
- `src/vectorstore/qdrant_client.py`: added `search()` (cosine similarity, optional server-side `trust_tier` filter) and `sample_random()` (for the cluster-anomaly reference sample below) — kept in this module rather than inlined in the policy engine since it already owns all other Qdrant I/O.
- `src/retrieval/policy_engine.py`: the core module.
  - `_gate(trust_tier, poison_score, config)`: pure decision function. `QUARANTINED` is an unconditional categorical drop unless `allow_quarantined_tier=True`; otherwise each tier has a `(downweight_threshold, hard_drop_threshold)` poison-score band — below it: `ALLOW` at full weight; inside it: `DOWNWEIGHT`, similarity score ramped linearly down to `downweight_floor_multiplier`; at/above it: `DROP`.
  - `FrequencyTracker`: in-memory, process-lifetime z-score tracker — flags a chunk_id whose cumulative retrieval count is `frequency_zscore_threshold` std-devs above the mean count across every chunk_id seen, gated by a `frequency_min_samples` cold-start guard. Flags by default, does not hard-drop (`frequency_hard_block=False`), reading PLAN.md's verb split ("gates ... flags ...") as intentional. Only records candidates that survive the poison gate (tracking already-dropped chunks would be redundant).
  - `retrieve(query, ...) -> RetrievalResult`: embeds the query, searches Qdrant (overfetched, tier-filtered), live-scores candidates via `DetectionPipeline.score_chunks()`, gates, frequency-checks survivors, returns up to `top_k` ranked by adjusted score. No LangGraph dependency — directly testable. `retrieve_node(state)` is a two-line adapter (`RetrievalState` TypedDict: `query`, `result`) — this is the **first LangGraph code anywhere in this repo**; Phase 5's generation node is the next consumer.
  - **Documented, not silently patched, limitation**: traced `score_cluster_anomaly` directly to confirm `reference_embeddings` only stabilizes the k-NN density sub-signal — DBSCAN stays self-referential by construction, and the final min-max normalization is *always* computed over the small per-query candidate batch regardless of any reference set. Passing a `sample_random()` reference sample (`cluster_reference_sample_size`) genuinely helps the k-NN sub-signal but does **not** fix the deeper train/inference scale mismatch (the classifier was trained on cluster-anomaly scores normalized over the full 280-chunk manifest). A real fix needs `cluster_anomaly.py` to support a fixed/anchored normalization range — Phase 9 territory.
- `eval/run_eval.py`: added `--stage retrieval [--compare-baseline] [--top-k N]`. `build_query_sets()` reconstructs `row_idx -> question` for clean chunks (which carry no `target_question`) by re-loading the underlying NQ sample pinned to `synthetic_poison_generator`'s own seed/params — verified directly against the real manifest: 20 ASR (attack) queries, 106 precision (clean) queries, 16 rows excluded from precision for target/clean overlap. ASR = fraction of attack queries where a targeting poison chunk reaches the final result set; retrieval-precision loss gates on the *relative* percentage (PLAN.md's plain "<15%", vs. ASR's explicit "-point" wording) with the absolute figure also reported. Results written to `eval/benchmarks/retrieval_eval_results.json`.
- Tests: `tests/retrieval/test_policy_config.py`, `tests/retrieval/test_policy_engine.py` (pure `_gate()` decision-table + `FrequencyTracker` z-score math, no Qdrant/models needed), `tests/retrieval/test_policy_engine_integration.py` (real Qdrant, scratch collection, confirms quarantined-tier exclusion end-to-end), `tests/eval/test_run_eval.py` (`build_query_sets()` asserted against the real manifest's 20/106/16 split, plus the pure ASR/precision helpers) — 34 new tests, all passing.

## Phase 5 — Generation, faithfulness check, minor-project eval — DONE

The end-to-end loop: gated context → LLM answer → per-claim NLI faithfulness check → FastAPI response. **This closes the minor-project gate** (Phase 4's ASR-reduction/precision-loss gate already passed; Phase 5 wires it into something actually queryable).

- `src/generation/config.py`: new `GenerationConfig` + `FaithfulnessConfig`, same file — mirrors `DetectionConfig` centralizing every Phase 3 submodule's knobs in one place, since `generate.py` and `faithfulness.py` are this phase's two submodules. Every threshold/model-name is `field(default_factory=...)`-backed per the established pattern, never a bare `os.getenv(...)` default.
- `src/generation/faithfulness.py`: `FaithfulnessChecker` wraps a `sentence-transformers` `CrossEncoder` NLI model (`cross-encoder/nli-deberta-v3-xsmall` by default — small/fast, same CPU-only-box reasoning as `distilgpt2` in Phase 3's perplexity scorer). `split_claims()` does simple regex sentence splitting (no nltk dependency). Entailment label index is read from the model's own `config.id2label` rather than assumed fixed-position — deliberately avoiding the exact bug class Phase 3 hit with pickled classifier modules. Per claim: NLI-scored against every context chunk, "grounded" if the best entailment probability clears `faithfulness_entailment_threshold`.
- `src/generation/generate.py`: `generate()` builds a citation-prompted message list from the Phase 4 policy engine's ranked survivors (capped/truncated independently via `generation_max_context_chunks`/`generation_max_chars_per_chunk`), calls `get_llm()` (never a provider SDK directly, per `CLAUDE.md`), then runs the faithfulness check on the answer. Short-circuits with **no LLM call** when the policy engine left zero survivors (returns `generation_no_context_answer` instead) — avoids inviting the model to answer from unverified parametric knowledge. `GenerationState` extends `RetrievalState`'s exact `query`/`result` fields (+ `generation`) so `retrieve_node`/`generate_node` compose in one LangGraph state schema.
- `src/api/main.py`: `build_graph()` compiles a `StateGraph(GenerationState)` wiring `retrieve_node -> generate_node -> END` — the first real LangGraph *graph* in this repo (Phase 4 only had a lone node). `POST /query` invokes it and returns `{answer, citations, faithfulness_score, ungrounded_claims, fetched_count, dropped_count, frequency_flags}`; `GET /health` for liveness.
- `eval/run_eval.py`: added `--stage generation` (`run_generation_eval`) and `--full-report` (`run_full_report`, runs detection + retrieval + generation and prints one combined summary). Deliberately **no invented cross-stage metric** — F1 comes from detection, ASR/precision@k from retrieval, generation contributes its own end-to-end ASR + faithfulness precision + latency; `--full-report` just runs all three and reports them together, per PLAN.md's literal "ASR / precision / F1 / latency report" wording. `generation_asr` reuses retrieval's manifest ground truth but sets a higher bar: an attack only counts as succeeding if a generated claim is NLI-entailed by a poisoned chunk (not just "survived retrieval gating"). Each generation-eval query is a real LLM + NLI call, so `--generation-asr-sample-size`/`--generation-precision-sample-size` cap cost the same way `--judge-sample-size` already did for Phase 3.
- New dependency actually installed (was already declared in `pyproject.toml` since the Phase 0 scaffold, just never `pip install`ed): `fastapi`, `uvicorn[standard]`.
- Tests: `tests/generation/{test_generation_config,test_faithfulness,test_generate}.py`, `tests/api/test_main.py`, plus 3 new pure-function tests in `tests/eval/test_run_eval.py` — 41 new tests, all passing. `test_faithfulness.py` loads the real (small) NLI model, same convention as `test_perplexity.py`/`test_embedder.py` (no mocked ML). The API tests use a fake compiled graph (monkeypatched `src.api.main._graph`) so they don't need a live Qdrant/LLM/NLI stack — `generate()`/`generate_node()` tests likewise use fake `llm`/`faithfulness_checker` objects via their existing dependency-injection params, same pattern Phase 4's `retrieve()` already established.
- **Real bug caught during live API verification** (not a hypothetical): the LLM sometimes emits its citation bracket *after* the sentence-ending period as its own fragment (e.g. `"...Naoroji. [clean-07331-0]"`), which the naive sentence splitter then treated as its own "claim" — NLI correctly finds no entailment for a bare citation, so it always scored as spuriously ungrounded and deflated `faithfulness_score`. Fixed with a `_CITATION_ONLY_RE` filter in `split_claims()` (verified live: the same real query went from `faithfulness_score=0.5` with one bogus `ungrounded_claims` entry to `1.0`/`[]` after the fix). Two new tests lock this in.
- **Known limitation, documented rather than silently patched** (see `run_generation_eval`'s docstring): `faithfulness_precision` conflates a *correct refusal* with a *hallucination*. The system prompt explicitly tells the model to say so when context is insufficient; when Phase 4's own retrieval precision@k (~0.35) means the truly relevant chunk isn't in the top-k for a given query, the model correctly abstains -- but that abstention sentence is still NLI-scored against context like any other claim, finds no entailment, and counts against the metric identically to a hallucination would. `faithfulness_precision` as currently measured is therefore a **lower bound** on true groundedness, not a hallucination rate. A real fix needs an abstention classifier ahead of the NLI check (risks its own false-negatives on hedged-language hallucinations) — left as future work, not bolted on under this phase's time budget.

## Phase 6 — Verifiable unlearning + deletion receipts — DONE

Delete-by-ID against Qdrant with real index compaction, a signed Ed25519 deletion receipt, and a "ghost vector" defense module that checks a deletion actually can't be reconstructed. Design went through an Explore pass over Phases 2–5's code, a Plan-agent pass, and independent verification against the real installed `qdrant-client==1.18.0` API before any code was written; plan approved via Plan Mode as required by `PLAN.md`.

- `src/unlearning/config.py`: new `UnlearningConfig` frozen dataclass, mirrors `DetectionConfig`/`PolicyConfig`'s exact pattern. Knobs: target collection, compaction thresholds, membership-check search width, reconstruction-attack decoy sample size/percentile, receipt directory, eval sample size.
- `src/unlearning/ghost_vector_defense.py`: two complementary checks, matching PLAN.md's split of "ghost_vector_defense.py defends against reconstruction" from "write an eval script that attempts reconstruction":
  1. `verify_unrecoverable()` — a membership-inference self-check: query Qdrant post-delete with the point's own true pre-delete vector and confirm it can't summon the point back. Proves deletion actually took effect at the index level, not just a soft tombstone.
  2. `attempt_reconstruction()` — a corpus-level reconstruction attack: does any surviving chunk still leak equivalent content via nearest-neighbor search? Judged against a **chance baseline built from decoy queries** (vectors from chunks sharing no `doc_id` with the deleted chunk), comparing the attack's best-neighbor similarity against the 95th percentile (config-driven) of the decoys' own best-neighbor similarities — not their mean. A naive mean-based comparison was considered and rejected during planning: a max-statistic (the attack) reliably beats a mean-of-random-draws (naive baseline) even with zero real leakage, which would make "reconstruction succeeds" read as true almost always regardless of ground truth.
- `src/unlearning/receipt.py`: signed JSON deletion receipts reusing `ProvenanceSigner` from Phase 2 directly — same Ed25519 keypair under `keys/`, no new crypto. Field set is `plan_2.md`'s literal `chunk_id, deleted_at, requester, signature` plus `point_id, collection_name, content_hash, found`, and both defense-check outcomes. `canonical_receipt_json()` uses `sort_keys=True` so `verify_receipt()` is reproducible regardless of dict/JSON round-trip order. `python -m src.unlearning.receipt verify --path <file>` independently verifies a receipt.
- `src/unlearning/delete.py`: `capture_point()` grabs a point's payload+vector *before* deleting (the only place it can be captured); `force_compaction()` forces Qdrant's optimizer to immediately vacuum the deleted point's segment via `OptimizersConfigDiff`, then **restores the collection's original optimizer thresholds afterward** — without the restore step, one delete call would permanently change the collection's optimizer behavior for every future write. `delete_with_receipt()` is the single end-to-end flow (delete → both defense checks → signed receipt) called identically by the CLI and the eval harness, so they can't drift apart. CLI: `python -m src.unlearning.delete --chunk-id <id>`, defaulting to the **live** collection (matches Phase 2's `qdrant_client.py` CLI's own default-to-live-collection convention) — running it for real does remove that chunk from the live 280-chunk demo corpus, restorable via `python -m src.vectorstore.qdrant_client upsert`.
- `eval/run_eval.py`: added `--stage unlearning` / `run_unlearning_eval()`. Runs the full delete/receipt/defense flow against a **disposable scratch collection** (`veritasrag_unlearning_eval_scratch`, seeded via `upsert_manifest()`, torn down in a `finally` even on exception) — the live corpus is never touched by the eval harness. Reports every Table VI metric `results.md`'s reporting session flagged as empty: deletion latency, compaction latency, receipt gen/verify latency, receipt validity rate, membership-check pass rate, reconstruction-attack success rate, and removal-precision@k before→after.
- **Real bug caught during live verification, not hypothetical**: the first live run showed `reconstruction_attack_success_rate=0.0` and every chance-baseline mean pinned at exactly `1.000` — too clean to be real. Root cause: decoy vectors were sampled *from* the same surviving-corpus pool used to build the reconstruction attack's search index, so every decoy trivially "found itself" as a similarity-1.0 nearest neighbor, saturating the chance baseline and making the check vacuously always pass regardless of actual leakage. Fixed by having `sample_decoy_vectors()` return decoy point IDs alongside their vectors, and excluding those same points from the index in `delete_with_receipt()` before running the attack. Re-verified against the real corpus with a targeted diagnostic (8 poison chunks, read-only) before and after the fix — post-fix numbers are non-trivial and match known corpus structure (PoisonedRAG same-target poison siblings, Phase 3's documented ~0.645 mean same-target similarity, occasionally register as genuine reconstructable leakage; unrelated content does not). Locked in with a regression test (`tests/unlearning/test_ghost_vector_defense.py::test_chance_baseline_uses_percentile_not_mean` for the percentile-vs-mean design choice, `tests/unlearning/test_delete.py::test_delete_with_receipt_end_to_end_found`'s `chance_baseline_mean < 0.999` assertion for the self-match fix specifically).
- **Second real bug caught during live verification**: Qdrant's server-side validation rejects `optimizers_config.vacuum_min_vector_number` below 100 ("value 0 invalid, must be 100 or larger") — `UnlearningConfig`'s first draft defaulted it to `0` (the most aggressive theoretical setting) and every live compaction call 422'd. Fixed by defaulting to `100`, confirmed against the live server, not just client-side docs.
- **New top-level directory, flagged per `CLAUDE.md`'s "say so explicitly" rule**: `receipts/` (gitignored, mirrors the existing `keys/`/`models/` generated-artifact convention) — not named in `PLAN.md` Part 3's repo layout. It's the natural home for the deletion audit trail Phase 7's dashboard is expected to read later.
- Tests: `tests/unlearning/{test_unlearning_config,test_ghost_vector_defense,test_receipt,test_delete}.py` (23 tests — pure-function tests for the reconstruction math and receipt sign/verify need no Qdrant; `test_delete.py` is a real integration suite against a scratch collection, same skip-if-unreachable pattern as `tests/vectorstore/test_qdrant_client.py`), plus 2 new pure-function tests for `eval/run_eval.py`'s new `_chunk_to_question_map()` helper in `tests/eval/test_run_eval.py`.
